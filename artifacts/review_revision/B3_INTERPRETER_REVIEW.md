# Fixed Minsky interpreter: contract review, 2026-09-13

This is a local source/contract review, not an independent reviewer report or a Gate E pass.

The host is the single 60-instruction `minsky_interpreter_program` under `run_vm_u` / `vm_apply_u`. The executable `minsky_total_config_encoding` chooses a sufficient width for every finite guest list, packs its instructions, and supplies code, width, guest PC and two natural counters only as data. The guest instruction language is precisely `MinskyInstrU`. This is a sibling of the physical word64 semantics; it does not alter or prove universality of that physical model.

The boundary relation permits arbitrary scratch and ambient fields but fixes guest registers, input encoding, running status and host PC. One-step simulation supplies strictly positive bounded overhead: INC0 16, INC1 20, JZDEC0 23/25, JZDEC1 27/29. Guest halt or falloff takes 12 host steps. Malformed raw opcode tags 5–7 take 24. Width zero is allowed when all encoded instructions are zero; the readback and outside-fetch proofs cover this case as well.

The inherited `interpreter_produces` is an instrumented relation: it includes a boundary trace and the guest's halt/falloff condition. Its theorem is retained, but is not used alone as evidence for arbitrary host result soundness. The new `interpreter_raw_produces` observes only an existential actual run, terminal PC/status, and the decoded guest PC/counters. `uniform_interpreter_raw_correct_total` proves its equivalence to `minsky_halts` over every finite guest program and natural configuration. The reverse direction follows from `uniform_interpreter_raw_sound`, whose only execution premise is that the actual runner reaches PC 60.

Raw soundness uses strong induction on host fuel. A live block has strictly positive length and returns to a represented boundary. If an earlier prefix had already reached terminal PC 60, all extensions would remain there, contradicting that boundary. Thus any terminal execution traversing a live block has enough fuel for that block, and induction applies to the remainder. A halting block's exact endpoint and terminal stability identify the actual returned configuration even if more or fewer host steps were supplied. No guest execution trace, segmentation, or assumed interpreter correctness occurs in this theorem's premises.

`uniform_interpreter_divergence_live_prefixes` states divergence as an available actual host instruction after every finite host prefix. It is equivalent to arbitrarily long guest-step prefixes. The proof uses determinism of the guest steps, finite bounds for halting guest runs, raw result correctness, and the host PC bound. It never treats a single exhausted fuel budget as divergence.

`uniform_interpreter_raw_frame` preserves the exact `minsky_ambient` projection for every raw prefix, including graph, CSRs, memory, scalar/tensor mu, error flag, logic accumulator, mstatus, witness and certification. The guest has no structural instructions and no guest ledger. This frame is not a theorem that simulates the full VM's structural operations or equates a simulated guest charge to host overhead. Existing errors are preserved, not required clear.

`uniform_interpreter_raw_never_malformed` excludes raw malformed outcomes for valid total encodings. The separate malformed-word contract covers tags 5–7; it does not classify every noncanonical binary representation as malformed. The guest trap predicate is explicitly false because the chosen guest has no trapping instruction. This is not a full-ISA fault contract.

Remaining applicability obligations: no checked universal-machine reduction or translation from the intended VM guest ISA into this exact guest language is present. No concrete effective specialization/recurrence instance for B4 is constructed. The physical FSM refinement, unchanged-ISA B2c target, independent review and final candidate reproduction remain separate. The original completion contract therefore cannot be marked finished on the strength of these results.

Validation commands, exit codes and source/evidence hashes are recorded in `b3_validation.json`; direct definitions/types/assumptions are in `b3_interpreter_report.txt`.

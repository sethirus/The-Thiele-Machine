`g_decode_guest_code_roundtrip` proves that decoding the existing
`program_to_nat (g_program p)` representation and reifying the twelve guest
instructions returns exactly `p`. `g_eval_guest_code` executes that decoded
program under an explicit fuel bound, and `g_eval_is_actual_vm_execution`
identifies the result with the guest fragment's actual `run_vm_u` execution.

`g_specialize p x` prefixes `GLoadImm 0 x 0` and relocates `p` by one address.
The generalized tail theorem proves

```coq
g_beh (g_specialize p x) y g mu <-> g_beh p x g mu
```

for every external input `y`. This is a behavioral s-m-n specialization, not
only an encoding identity.

## Exact residual blocker

The evaluator is a verified Coq dispatch function over numeric code. It is not
an instruction that a running guest program can invoke. Kleene's construction
also needs the numeric code-producing specialization function to be
represented by a guest program. `g_specialize` is an effective Coq syntax
constructor, but no theorem makes that constructor executable inside the guest
fragment.

Consequently the Round 1 fixed-point statement remains unchanged and BLOCKED.
Calling `g_eval` from the proof at the meta-level would assume precisely the
internal execution capability the theorem is meant to derive.

## Three strategies in this round

1. **Decode and dispatch the existing full-program number.** This succeeded as
   `g_eval`, with an actual-execution theorem, but remains host/meta-level.
2. **Derive s-m-n from relocation.** This succeeded as `g_smn`, but the code
   constructor is not internally represented.
3. **Reuse the fixed host interpreter `U` as the guest evaluator.** `U` is an
   actual VM program, but it uses registers 4 through 15 for code, width,
   status, ledger, and scratch. It is not a well-formed program of the
   four-register guest fragment it interprets, so inserting it would change
   the named machine. A self-contained interpreter would need an inaccessible
   saved-input channel or an encoded register file, plus a proof that the
   specialization-code constructor runs inside that same fragment.

## Hollowness checks

- Definitional: decoder round trip follows the existing injective encoding but
  checks an explicit partial reifier. `g_smn` is semantic and uses relocation
  and termination behavior.
- Built in: `g_eval` invokes `g_run` by definition, so its execution theorem is
  a verified dispatch boundary, not evidence that a guest can call it. The
  report does not use it to close the fixed point.
- Vacuity: identity-transformer representability remains inhabited; concrete
  guest programs decode, evaluate, and specialize.
- Swap: the same relocation proof works for any guest program and constant
  input; the obstruction depends on interpreter/fragment closure, not the
  program's name.
- Adversarial read: the result supplies an external verified evaluator and
  semantic s-m-n. It does not claim an `EVAL` opcode, an internally represented
  specialization-code function, or a VM recursion theorem.

The new acceptance test was observed failing before the proof file existed.
All four proved theorem assumption reports are closed under the global
context. The three new strategies are distinct from the three recorded in
Round 1 and isolate the remaining implementation contract.

Root cause, confirmed via multiple isolated `coqc` repros (2026-09-15 night, building `preserved_morph_ext` in TableInvariantsPreserved.v): this codebase names *many* bit-widths that are numerically identical but are separate `Definition`s (`DescIdxSz := 4`, `CouplingDescIdxSz := 4`, `MorphTableIdxSz := 4`; `MorphTableNextIdSz := 5`, `DescTableNextIdSz := 5`, `CouplingPairCountSz := 5`). `word`-typed functions (`weq`, `wlt_dec`, `wordToNat`, `zext`, `natToWord`) carry an *implicit* `sz` argument. Two syntactically different but *convertible* instantiations of that implicit (e.g. `@weq 4 x y` vs `@weq DescIdxSz x y`) are accepted everywhere by the type checker (via delta-conversion) — but `destruct`/`rewrite` match by **syntactic** term structure, not conversion. So a `destruct`/`rewrite` call whose own elaboration path picks a different (but equal) instantiation than the one already baked into the surrounding expression will silently fail to simplify the goal (leaving it looking unchanged), or `rewrite` will report "Found no subterm matching" even though the term is visibly present under the `#`-hiding pretty-printer.

**How the mismatch actually arises** (the load-bearing insight): the implicit `sz` on `weq A B` is inferred from whichever argument's type is *already fixed* first — normally the **first explicit argument**, checked left-to-right. So `destruct (weq i s)` (i's type dominates) differs from `destruct (weq (natToWord CouplingDescIdxSz 0) cd)` (the literal's *explicit* sz argument dominates) differs again from `destruct (weq cd cd)` (cd's own "home" type, e.g. bare `word 4` from `split1 4 1 (...)`, a `set`-bound term with no named tag at all). Three genuinely different sources of "the same" sz. A term produced by **substituting into an already-elaborated definition's body** (e.g. `hw_coupling_ref_ok`'s own internal `weq d (natToWord DescIdxSz 0)`, or `put_vector`'s own internal `weq w idx` fixed to *bare* `word 4` regardless of what gets substituted later) keeps **that definition's own** sz tag forever, independent of what "natural" type the substituted variable would otherwise carry. `apply lemma` on a *goal* (not `apply lemma in H`) can also silently re-tag: unifying the lemma's `forall sz (a b : word sz), ...` against two arguments whose *own* types differ only by naming picks one canonical sz for the produced subgoal, which may not match a *separately, freshly-stated* hypothesis about the same value (this broke `Hcdn`/`Hdnd`-vs-goal combinations after `apply lt_wlt`/`apply coupling_ref_ok_of_lt` repeatedly).

**Diagnosis recipe** (fast, don't skip): when `rewrite` says "Found no subterm matching" or a bare `lia`/`reflexivity` right after a `destruct` fails with "Unable to unify ... " showing the *whole, unreduced* expression (not a simplified branch), suspect this. Confirm by temporarily replacing the failing tactic with `exact I` (a deliberately wrong term) — the resulting error dumps the *exact* elaborated goal/hypothesis types with all implicit args spelled out in prefix form (`#(hw_coupling_desc_next_id b2)` etc.), letting you compare the actual sz tag against what the fix attempt used. This was the single fastest way to actually see the mismatch; guessing from the pretty-printed `#`-notation alone is not enough since it hides implicits.

**Fixes, in order of preference**:
1. **State the lemma/helper's binder with the *exact* named type the definition-under-unfold uses**, not whatever the argument's "other" use would infer (e.g. `coupling_ref_ok_of_lt : forall b (x : word DescIdxSz), ...` — not `forall b x, ...` — because `hw_coupling_ref_ok`'s own domain is `word DescIdxSz`; letting Coq infer `x`'s type from a *different* co-occurring use like `hw_coupling_desc_valid_table b x` silently picks `CouplingDescIdxSz` instead and breaks the internal `destruct`s). This is the real fix, used for `coupling_ref_ok_of_lt` in `TableInvariantsPreserved.v`.
2. **When applying such a lemma to a term whose "natural" type differs** (e.g. `apply coupling_ref_ok_of_lt` where the goal's own index is a bare-`word 4` `cd`), the produced subgoal's implicit tag comes from the *lemma's* binder, not from `cd`'s natural type — so a later `rewrite Hcdn`/`lia` using a *freshly, separately stated* `Hcdn : wordToNat cd = ...` (which used cd's own natural bare-4 tag) will mismatch. Fix with `change (@wordToNat <lemma's-tag> cd) with (wordToNat cd)` immediately after `apply`, before touching it with anything else — `change` uses full conversion so it always succeeds regardless of which tag is "right"; `rewrite`/`lia` never do.
3. **`lia` can still fail ("Cannot find witness") even after a `change` makes the atoms textually identical**, for reasons not fully root-caused this session (confirmed via isolated repro: `rewrite Hcdn in Hlt1` *succeeds* syntactically, turning `Hlt1` into a literal `X < X`, yet bare `lia` right after still errors). Workaround: do the substituting `rewrite` explicitly first to force the hypothesis into a *manifestly* trivial shape (`X < X`, `X < X+1`, etc.), then close with a **named library lemma** instead of `lia` — `Nat.lt_irrefl`, `Nat.lt_lt_succ_r` (composed with `Nat.add_1_r` since `X+1` is *not* definitionally `S X` for abstract `X` — `Nat.add` recurses on its first argument), etc. This was needed twice in `Hgrow`'s proof and was the actual unblocking step, not the `change`.
4. **`Definition`s with generic `word 4` domains written by hand** (`put_vector`, this codebase's own combinator) always keep `sz = 4` bare, forever, regardless of what index type gets substituted later — so *every* index comparison/lookup coming from `unfold put_vector` needs an explicit `@weq 4 x y` in the matching `destruct`, never a bare `destruct (weq x y)`, even if `x`'s "natural" type looks identical.
5. **When one variable is compared against the same `cd`/`s` in two structurally different surrounding contexts within one clause** (e.g. `hw_coupling_desc_valid_table`'s `put_vector`-based mux, bare-4-tagged, *and* `StepFieldsMorph`'s own hand-written label-table mux, `CouplingDescIdxSz`-tagged, both keyed on the *same* logical "is this the newly-written index?" question) — a single `destruct` cannot resolve both occurrences at once. Do **two separate `destruct`s** (one per tag), and discharge the "impossible" cross-branches via `exfalso; apply <negation>; exact <other-tag's-equality-proof>` (again relying on `exact`'s full-conversion robustness to bridge the two tags). Needed for `hwb_labels_represented` in `preserved_morph_ext` (clause 9), not needed for clauses that only ever go through `put_vector` (base/count/valid/next_id — bare-4 throughout, one destruct suffices).
6. `wordToNat_wminus_le`'s `sz` parameter is **explicit**, not implicit (`forall sz (a b : word sz), ...`) — a very easy, unrelated-looking bug to introduce by habit (most of this codebase's other word helpers have `sz` implicit); passing `(natToWord 5 out)` as if it were the first explicit arg silently tries to unify it as `sz` itself, producing an opaque "term X has type word 5 while expected nat" error far from the real mistake. Always check a lemma's actual `Print`ed signature before assuming implicit-argument shape from sibling lemmas.

This class of bug cost the majority of the session's wall-clock time building [[c2-step-refinement-pipeline]]'s `preserved_morph_ext` (MORPH_EXT's table-invariant preservation, the first of the 8 "hard" `RetireMaster.admitted` constructors requiring real allocation/FSM reasoning rather than pure frame). Expect it again, identically, for `preserved_compose_ext` (uses `CouplingComposeRetire.v`'s analogous FSM, same `put_vector`/named-constant mix) — apply the fixes above proactively rather than rediscovering them.
